# MacRemote v0.5.3 Updater and Brightness Corrective Design

## Goal

Make the native Android updater self-explanatory and make brightness controls reliable when display topology changes, without changing the server API for older clients.

## Evidence

- In v0.5.0 through v0.5.2, the Devices-screen update button only stores a discovered release. The download action is rendered on the Remote screen, so a successful check appears to do nothing.
- The live v0.5.2 server reports only the built-in display. Built-in dim and brighten calls work, but an external target returns HTTP 200 with `ok:false` and `display_unsupported:true`.
- The Android client discards brightness response bodies. A migrated or disconnected display target therefore produces a silent no-op.
- Android refreshes `/status` after a brightness step but does not refresh `/displays`, leaving external DDC or gamma levels stale in the UI.

## Considered Approaches

1. Show a snackbar after update discovery and brightness failures. This is small, but leaves update actions split across screens and does not repair stale targets.
2. Validate display targets in Android, decode brightness results, refresh display state, and render the update action where the check begins. This fixes the causes while preserving the existing wire API. This is the selected approach.
3. Change brightness semantic failures to HTTP errors and redesign the update service. This is cleaner at the protocol level but risks breaking older clients and is unnecessary for the corrective release.

## Design

### Update flow

- Track whether a manual update check is running.
- Keep the check button on the Devices screen, disable it while checking, and show visible checking text.
- When a release is found, render its download/install action immediately below that button on the same screen.
- Keep the Remote-screen update banner for automatic discovery and existing muscle memory.
- Preserve the existing two-step Android unknown-source permission flow, but keep the install action visible after returning from Settings.
- Surface all check, download, integrity, permission, and installer-launch failures through the existing snackbar.

### Brightness flow

- Resolve a saved brightness target against every successful `/displays` response.
- Preserve a valid target; otherwise choose the built-in display, or the first reported display when no built-in panel exists, and persist the repair.
- Decode brightness endpoint responses into a typed result instead of treating every HTTP 2xx as success.
- Surface `display_unsupported` as a concise user-facing message.
- Refresh `/displays` after brightness steps and absolute changes so gamma/DDC values remain authoritative.
- Preserve built-in hardware-key brightness behavior and all existing server routes.

## Tests

- Add pure JVM tests for target repair and brightness-result decoding.
- Add reducer tests for update checking, available, current, and failure presentation states.
- Add server regression coverage for unsupported-display response semantics.
- Run Android unit tests, lint, debug/release builds, server tests, extension tests, APK signing/version inspection, and an upgrade install check where an Android target is available.
- Review the final diff with Claude and resolve confirmed critical or warning findings before release.
